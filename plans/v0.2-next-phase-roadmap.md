## 1. Executive Summary

Evolve llm-vcr from a **sync, exact-match HTTP replayer** into a **production-grade LLM test harness**: SSE streaming replay, multi-step tool-call loops, async httpx, semantic request normalization for OpenAI and Anthropic, PyPI distribution, and an idiomatic pytest fixture API.

## 3. Milestone Breakdown

### Milestone M1 — SSE Streaming Replay (v0.2.0)

**Goal:** Record and replay Server-Sent Events streams from OpenAI/Anthropic streaming endpoints chunk-by-chunk.

#### Deliverables

- [ ] `src/llm_vcr/streaming.py` — SSE parser, chunk collector, replayer
- [ ] Extend cassette schema with `streaming: true` and `chunks: []` per interaction
- [ ] `VCRTransport` detects `Accept: text/event-stream` or `stream: true` in body
- [ ] Replay mode yields synthetic `httpx.Response` with iterable byte stream
- [ ] Record mode captures raw SSE lines with timestamps (optional, for debugging)
- [ ] `@llm_vcr` works with `client.stream("POST", ...)` usage pattern
- [ ] Example cassette: `tests/cassettes/test_streaming.yaml`
- [ ] Tests: parse SSE, replay full stream, partial stream abort

#### Cassette Schema Extension

```yaml
interactions:
  - method: POST
    url: https://api.openai.com/v1/chat/completions
    request_body: { model: gpt-4o-mini, stream: true, messages: [...] }
    streaming: true
    chunks:
      - "data: {\"id\":\"1\",\"choices\":[{\"delta\":{\"content\":\"Hi\"}}]}\n\n"
      - "data: [DONE]\n\n"
    status_code: 200
```

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | Replay streaming response yields identical chunk sequence to recording | Integration test |
| AC2 | Non-streaming interactions unchanged (backward compatible cassettes) | Existing 3 tests pass |
| AC3 | Missing chunk in cassette raises clear `RequestError` | Unit test |
| AC4 | OpenAI `data: [DONE]` sentinel handled correctly | Fixture test |

#### Dependencies

- httpx stream API (`client.stream`, `response.iter_lines()`)
- OpenAI streaming format documentation

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Provider SSE format differences (OpenAI vs Anthropic) | High | Provider tag in cassette; M5 adapters |
| Chunk timing-sensitive client code | Medium | Optional `--streaming-realtime` delay mode |
| Large streams bloat cassette files | Medium | Optional chunk compaction; gzip cassettes (future) |

**Estimate:** 1.5–2 weeks

### Milestone M2 — Tool-Call Multi-Step Loops (v0.2.0)

**Goal:** Support agentic test scenarios where one test triggers multiple sequential LLM calls (tool call → tool result → follow-up completion).

#### Deliverables

- [ ] Sequence-aware matching: ordered interaction list consumed per test
- [ ] `Cassette.interaction_index` tracker (thread-local or transport state)
- [ ] `@llm_vcr(sequential=True)` — enforce strict interaction order
- [ ] `@llm_vcr(sequential=False)` — match any remaining interaction by hash (default, v0.1 behavior)
- [ ] Tool-call fixture: 3-step loop (prompt → tool_call → tool_result → final)
- [ ] `tests/test_tool_loop.py` — multi-interaction replay test
- [ ] Document cassette authoring for agent loops

#### Multi-Step Flow

```
Test start → interaction[0] (initial completion + tool_calls)
           → interaction[1] (follow-up with tool result)
           → interaction[2] (final text response)
Test end   → assert all interactions consumed (no unused, no deficit)
```

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | 3-step tool loop test passes in replay mode without network | `test_tool_loop.py` |
| AC2 | Out-of-order request in sequential mode raises explicit error | Unit test |
| AC3 | Unused interactions at test end emit warning (configurable strict) | pytest warning test |
| AC4 | Record mode captures all steps in single cassette file | Manual record run |

#### Dependencies

- M1 not strictly required but streaming tool loops benefit from combined release
- OpenAI tool_calls response schema in fixtures

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Parallel test calls share transport state | Medium | Thread-local interaction index; document xdist usage |
| Non-deterministic tool-call ordering from model | High | Sequential mode for tests; semantic matching in M4 |
| Cassette hand-editing complexity | Medium | CLI `llm-vcr inspect` command (optional v0.3) |

**Estimate:** 1.5–2 weeks

### Milestone M4 — Semantic Request Matching (v0.4.0)

**Goal:** Match requests by normalized semantic content instead of exact JSON bytes — tolerate model alias differences, whitespace, and message ordering where safe.

#### Deliverables

- [ ] `src/llm_vcr/matching/` — matcher interface + exact + semantic implementations
- [ ] `SemanticMatcher` normalizes: model aliases (`gpt-4o-mini` ≡ `gpt-4o-mini-2024-07-18`), message arrays, tool definitions
- [ ] `@llm_vcr(matcher="semantic")` opt-in per test; `"exact"` remains default
- [ ] Optional header inclusion in match key (`Authorization` excluded by default)
- [ ] `llm-vcr diff` CLI — show why two requests don't match
- [ ] Provider hooks stub (filled in M5): `normalize_openai_body()`, `normalize_anthropic_body()`
- [ ] Tests: alias match passes, substantive body change fails

#### Normalization Rules (initial)

| Field | Normalization |
|-------|---------------|
| `model` | Resolve via alias table |
| `messages[].content` | Strip trailing whitespace |
| `temperature` | Ignore if absent vs default |
| `stream` | Include in match key |
| `tools` | Sort by function name for matching |

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | Same prompt, different model alias string → match under semantic mode | Unit test |
| AC2 | Changed user message content → no match | Unit test |
| AC3 | Exact mode behavior unchanged (default) | Regression suite |
| AC4 | `llm-vcr diff` prints human-readable mismatch reason | CLI test |

#### Dependencies

- Model alias tables maintained in provider modules (M5)
- Document upgrade path for existing cassettes (exact → semantic)

#### Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Over-normalization causes false-positive matches | Medium | Conservative rules; explicit opt-in |
| Under-normalization frustrates users | Medium | Expand alias tables from community PRs |
| Anthropic vs OpenAI schema divergence | High | Provider-specific normalizers in M5 |

**Estimate:** 2 weeks

### Milestone M5 — PyPI + Provider Adapters + pytest Fixture API (v0.5.0)

**Goal:** Publish to PyPI, ship first-class OpenAI and Anthropic adapters, and provide idiomatic pytest fixtures alongside the decorator.

#### Deliverables

- [ ] PyPI publish pipeline (GitHub Release → `pypa/gh-action-pypi-publish`)
- [ ] `src/llm_vcr/providers/openai.py` — URL patterns, body normalization, streaming quirks
- [ ] `src/llm_vcr/providers/anthropic.py` — Messages API normalization
- [ ] Auto-detect provider from URL hostname
- [ ] `@pytest.fixture` `llm_vcr` — yields configured `httpx.Client` with cassette name from test node id
- [ ] `@pytest.fixture` `llm_vcr_async` — async counterpart
- [ ] Fixture params: `cassette_name`, `record_mode`, `matcher`, `provider`
- [ ] `pyproject.toml` optional extras: `llm-vcr[openai]`, `llm-vcr[anthropic]`
- [ ] README migration guide: decorator → fixture
- [ ] Example projects: `examples/openai-chat/`, `examples/anthropic-messages/`

#### Fixture API (target)

```python
def test_chat(llm_vcr: httpx.Client) -> None:
    resp = llm_vcr.post("https://api.openai.com/v1/chat/completions", json={...})
    assert resp.status_code == 200
```

#### Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|--------------|
| AC1 | `pip install llm-vcr` from PyPI installs and runs tests | Post-publish smoke |
| AC2 | OpenAI adapter normalizes chat completion bodies for semantic match | Provider unit tests |
| AC3 | Anthropic adapter normalizes messages API bodies | Provider unit tests |
| AC4 | Fixture API passes same 3+ integration tests as decorator | Parallel test suite |
| AC5 | Provider auto-detect works for both official API base URLs | Unit test |
| AC6 | Version tagged release on GitHub matches PyPI artifact | Release checklist |

#### Dependencies

- M4 semantic matcher (providers plug in normalizers)
- PyPI account + trusted publishing configured

#### Risks

| Risk | Likelihood | Mitigation |

**Estimate:** 2–2.5 weeks
